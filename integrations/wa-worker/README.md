# Capital Brix WhatsApp worker

Our own number, our own session, our own code.

## Why this exists

The attendance reports were going out through a Baileys worker shared with
Call Pro AI — one WhatsApp login serving two companies. That cost us twice:

- On **22 September 2026** a `Daily Pulse | Fanbe` message generated by Call
  Pro AI left the founder's WhatsApp to an outside number and read as though
  Capital Brix had sent it. It did not come from our code, but nothing on our
  side could have stopped it either.
- Earlier, that worker's own `toJid()` stripped `@g.us` off group addresses,
  so **every group report was acknowledged with a message id and delivered to
  nobody** for as long as the group was configured.

Neither was a bug in the Capital Brix repo, and neither was ours to fix. A
number of our own ends the ambiguity permanently: one company per session, and
a codebase whose behaviour can be read rather than guessed at.

## What it does, and deliberately does not

It **sends**. It registers no message handler, does not sync history and
answers nobody. A number linked here cannot be used to read anyone's
conversations, and there is no code path by which another product's message
could leave through it.

It speaks exactly the contract the `wa-session` Edge Function already calls,
so switching over changes **two secrets and nothing else** — no change to
`attendance-whatsapp`, the cron jobs, or `/admin/whatsapp`.

| Route | Auth | Answers |
|---|---|---|
| `GET /health` | none | per-state session counts |
| `GET /status` | bearer | this session's state and number |
| `GET /qr` | bearer | pairing square as a data URI |
| `POST /reconnect` | bearer | start a socket so a QR appears |
| `POST /send` | bearer | `{ to, text }` → `{ ok, id }` |
| `GET /groups` | bearer | groups this number can post to, with JIDs |

`/health` carries no bearer on purpose: it must keep answering when the token
is wrong or the session is dead, because those are exactly the moments
somebody is asking. It reveals a count per state and nothing about the
account.

## Not on Vercel — and Vercel will keep offering

Vercel emails "a new project in fadoomotivation-pixel/cap is available to
import" for any folder that looks like a server, and on **23 September 2026**
it offered this one as `wa-worker · express`. **Do not import it.** The button
works; the worker does not.

Two things this needs that a serverless platform does not have:

1. **A process that stays up.** Baileys holds an open WebSocket to WhatsApp
   for as long as the number is linked. A Vercel function is started for one
   request and torn down after it — there is nothing for the socket to live
   in, so the session would be logged out between every send.
2. **A disk that survives.** `WA_AUTH_DIR` *is* the WhatsApp account
   (`useMultiFileAuthState`). On Vercel the filesystem is read-only apart from
   `/tmp`, which is discarded — so every request would find no credentials and
   ask for a fresh QR. Nobody can scan a code that is regenerated per request.

The failure would not be loud, either, which is the part worth knowing: the
import succeeds, the URL answers, `/health` returns, and sends fail or vanish.
That is the same shape as every other WhatsApp failure in this module — a
message id is not delivery.

**What it needs instead** is any box that runs a process and keeps a
directory: a small VPS with pm2 or systemd (below), or a container platform
with a mounted volume — Railway, Render, Fly.io — with the volume mounted at
`WA_AUTH_DIR` and the same care about the directory being the account. The
office PC can host it, but it already took the attendance register down for
five days by being switched off, so it is the weakest of the options.

`vercel.json` in this repo is the *website's* config and has nothing to do
with this folder. The `cap` Vercel project builds `vite` from the root and
never looks in `integrations/`.

## Setting it up

**1. Get a SIM for the company.** Any number that is not the founder's
personal one and not Call Pro AI's. It needs to receive one SMS or call to
activate WhatsApp, and then it can sit in a drawer — the session survives on
its own once linked.

**2. Install and run it** on a box with a public HTTPS address:

```bash
git clone <this repo> && cd integrations/wa-worker
npm install
cp .env.example .env     # then fill WA_TOKEN
node server.js
```

Keep it alive with pm2 or systemd:

```bash
pm2 start server.js --name capitalbrix-wa --update-env
pm2 save
```

**3. Put HTTPS in front of it.** Supabase Edge Functions will not call a
plain-HTTP URL. A subdomain such as `wa.capitalbrix.co.in` pointed at the box,
with Caddy or nginx terminating TLS and proxying to `PORT`, is enough. Caddy
needs one line:

```
wa.capitalbrix.co.in {
  reverse_proxy localhost:8099
}
```

**4. Link the phone from `/admin/whatsapp`.** Once the two secrets below are
set, "Show pairing code" mints a QR. Scan it from the **new** number:
WhatsApp → Settings → Linked devices → Link a device.

**5. Point Supabase at it** — Project Settings → Edge Functions → Secrets on
project `rqgkzamuohdvttnkluzn` (**check the ref in the URL**; the same org
holds `Fanbe-CRM` / `mfgjzkaabyltscgrkhdz` and it is not ours):

```
WA_WEBHOOK_URL   = https://wa.capitalbrix.co.in/send
WA_WEBHOOK_TOKEN = <the WA_TOKEN from .env>
```

`wa-session` derives its base URL by stripping `/send`, so nothing else needs
setting.

**6. Add the new number to the WhatsApp group.** WhatsApp only lets an account
post to groups it is a member of. Until the new number is in CAPITAL BRIX
INFO, the group messages cannot be delivered — and the founder's two need the
new number too, so put it wherever they should land.

**7. Prove it end to end**, in this order — each step rules out one thing:

```sql
-- the cron leg and CRON_SECRET
select cb_send_attendance_report('attendance');
select * from net._http_response order by id desc limit 1;

-- what actually happened to the message
select * from cb_report_log order by sent_at desc limit 5;
```

Then send a real one from `/admin/whatsapp` → Send a test, to your own
number, and **look at the phone**. A message id is not delivery — that lesson
cost this module a fortnight, and it is the only check that settles it.

## Things not to change

- **`toJid` returns an address containing `@` untouched.** This is the group
  bug. Anything that "normalises" a JID by stripping non-digits turns
  `120363…@g.us` into a personal address that does not exist, and Baileys
  answers with a message id anyway.
- **A send on a disconnected session answers 503, never `ok`.** The caller
  logs the result, and a cheerful `ok` is how three weeks pass before anyone
  notices nobody has seen a report.
- **A `loggedOut` close does not retry.** The phone unlinked the device and
  the stored credentials are dead; looping hides the one fact that matters,
  which is that somebody has to scan again.
- **`WA_AUTH_DIR` is the account.** Whoever copies that directory can post as
  this number. Keep it off any web-served path, out of git, and out of
  backups that others can read.
